# v0.32.0

Nothing in this release needs a consumer change. The sandbox edge is opt-in
and off by default; every existing session launches as before.

- `Sandbox.Edge` (with `session.Edge`: `AllowHosts`, `ClaudeToken`, `BaseURL`)
  runs a Codex or Claude CLI session's whole process tree inside the
  harness's own command sandbox on macOS, with the CLI's own sandbox switched
  off inside it. Writes are limited as the session sandbox limits them; the
  workspace's `.git`, `.codex`, `.agents`, `.claude` and `.mcp.json`, and the
  runtime's credential, config and instruction files, stay protected; the
  owner's login home is denied.
- The session's only egress is a per-session credentialed CONNECT proxy on
  loopback, forwarding to the engine's provider hosts (Codex: api.openai.com,
  chatgpt.com; Claude: api.anthropic.com) and any `AllowHosts`. Direct TCP,
  UDP and DNS are denied. Codex's login is imported one way; its refresh host
  is blocked, and a blocked refresh fails as `edge_login_refresh_blocked`.
- Before any credentialed launch a canary runs the installed binary with
  disposable homes, dummy credentials and a fake provider, drives one real
  native shell call, and judges reads, writes, exec, protected files, network
  and DNS denial against positive off-machine controls, and loopback.
  Checked against Codex 0.166.0 and Claude Code 2.1.316.
- `harness.SandboxEdge` reports support: Unknown on macOS, proved at each
  open by the canary, since no credentialed provider turn has been run;
  refused on Linux (`edge_unavailable`) and Windows. Provided skills are
  refused under the edge, as their folders lie outside its read set.
- Not yet verified: a real ChatGPT-login session under the edge. A Codex
  installation inside the login home (`~/.codex`) is refused with
  `edge_conflict`; use one outside it.
