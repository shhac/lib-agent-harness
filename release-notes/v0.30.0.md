# v0.30.0

Nothing in this release needs a consumer change. `session.Sandbox` gains the
`Subagents` field, which affects only positional `Sandbox` literals. A sandbox
without it launches with the same arguments and keeps its earlier reference
digest.

- `Sandbox.Subagents` (opt-in, off by default) lets a sandboxed session use its
  CLI's own subagents. Nothing else about the sandbox changes. The library
  proves no inheritance: subagents get the CLI's own sandbox and whatever else
  the CLI documents.
  - Claude Code gains its `Agent` tool through `--tools` and a bare allow
    rule. Checked against Claude Code 2.1.316, whose init frame still reports
    it as `Task`. Subagents take their tools from the session's, under the same
    deny rules, `--disallowedTools` and OS sandbox, so web and MCP tools stay
    out unless the session has them. With every settings source dropped, only
    built-in agent types load, never the workspace's or the operator's
    `.claude/agents`. The Agent tool's `isolation: "worktree"` has the CLI
    itself, outside the OS sandbox, create a git worktree under the workspace
    and a branch in `.git`, even in a read-only sandbox.
  - Codex runs with `agents.enabled=true` and `features.multi_agent=true`,
    with `multi_agent_v2` still off. Both keys were checked against codex-cli
    0.166.0. Spawned agents are assumed to run as threads of the same
    app-server under the session's permission profile, as Codex documents
    subagents inheriting its sandbox, approval policy and permissions; this is
    not verified.
  - A caller asks `harness.Support(e, harness.Session,
    harness.SandboxedSubagents)` first. It is native for Claude and Codex
    sessions on macOS and Linux, and unsupported on Windows and for every
    other engine, all of which already refuse a sandboxed session.
  - A reference and the cached sandbox proof both include `Subagents`: a
    resume cannot switch it, and a proof made without it is not reused for a
    launch with it.
